# CloakroomEscrow v3: verification and audit report

Target: `src/CloakroomEscrow.sol` and `src/Pallas.sol` (final versions, with the L-01 and I-01 fixes).
Toolchain:
- solc 0.8.30 (via_ir, optimizer 200, evm cancun)
- forge / anvil 1.2.3-stable
- halmos 0.3.3, with the z3 solver and `--solver-threads 1`
- slither-analyzer 0.11.6

Every run below was made on the final source, one job at a time. Raw logs are in `audit/logs/`.

## 2. Halmos specifications

The escrow proofs run against `test/generated/CloakroomEscrowStubbed.sol`. This is generated by
`audit/gen_harnesses.sh` and is byte-identical to `src/CloakroomEscrow.sol`, except that it
imports `PallasStub.sol`. In the stub, `isOnCurve` and `isDiscreteLogOf` keep their range guards,
but the curve relation is an uninterpreted predicate. The escrow proofs therefore hold for **any**
behaviour of the curve check. They say nothing about the curve arithmetic, which §3 covers.

**Single-call specifications** (`EscrowSMHalmos`, 13 proved; arguments, caller, time and pre-state
are symbolic):
- `check_open_iff`, `check_setReady_iff`, `check_commitClaim_iff`, `check_claim_iff`,
  `check_refund_iff`: each function succeeds **if and only if** its documented guard holds, and
  then produces exactly the documented effects, including exact credits.
- `check_anyCall_transitionsAndMaker`: any call moves a swap only along the state machine's edges,
  never changes `maker`, and `Claimed` and `Refunded` are absorbing.
- `check_windowsDisjoint`: at no instant are both a commit/claim door and a refund door open.
- `check_refund_OpenReady_neverAtOrAfterT2` and `check_commitClaim_fromOpen_onlyAtOrAfterT2`:
  the punish window. After t2 an Open or Ready swap can only be locked, never refunded, and an
  Open swap can be locked only from t2.
- `check_commitClaim_lockTimeWindows`, `check_commitDigest_injective`,
  `check_open_cannotTouchOtherMakersId`, `check_withdraw_exact`.

**Reentrancy** (`EscrowReentryHalmos`, 2 proved). During `transferFrom` and `transfer`, a
malicious token checks that the escrow's effects are already applied. It then re-enters the escrow
with **arbitrary symbolic calldata**:
- `check_open_CEI`: the swap is already `Open` when tokens are pulled.
- `check_withdraw_CEI_and_noDoublePay`: the credit is already 0 when tokens are paid, so a nested
  withdraw pays nothing.

**Sequences** (`EscrowSeqHalmos`). Each step warps by a symbolic dt < 2^40, then calls one of the
six external functions with symbolic arguments and a symbolic caller (2 makers, 2 others).
Reverting calls are pruned with `vm.assume(ok)`. This is sound: a reverted call leaves the state
unchanged, so the states reachable with ≤ N calls are exactly those reachable with ≤ N successful
calls. After every prefix, the following are asserted:
- per-swap state machine consistency;
- conservation: the escrow balance equals the unsettled amounts plus outstanding credits;
- credits never exceed deposits;
- token supply is unchanged.

Amounts are bounded below 2^96. USDC's supply is about 2^56.

| Run | Paths | Time | Result |
|---|---|---|---|
| depth 1 | 35 | 1.4 s | proved |
| depth 2 | 663 | 41 s | proved |
| depth 4, one swap id | 624 | 73 s | proved |
| directed depth 6: open, ready, warp, commit, claim, withdraw (all arguments symbolic) | 194 | 81 s | proved |
| depth 3, unrestricted | — | > 48 min | **not proved** (path explosion; killed) |

**Witnesses** (`EscrowWitnessHalmos`). Each witness asserts that a good outcome is *impossible*. A
counterexample (reported as FAIL) therefore proves the outcome is reachable, which shows the
specifications above are not vacuous. All four were found:
- claim via Ready;
- claim via the punish path from Open;
- each of the three refund doors;
- withdraw after a claim pays the taker.

Commands:
```
./audit/run_halmos.sh EscrowSMHalmos
./audit/run_halmos.sh EscrowReentryHalmos
./audit/run_halmos.sh EscrowWitnessHalmos
./audit/run_halmos.sh EscrowSeqHalmos --function check_seq_depth1   # likewise depth2, depth4_oneSwap, claimPathThenWithdraw
./audit/run_halmos.sh PallasHalmos
```

## 3. Curve arithmetic (`src/Pallas.sol`)

Symbolic execution cannot reach 255-bit scalar multiplication. The library is checked as follows.

1. **Exhaustively on small curves.** `audit/gen_harnesses.sh` produces copies of the **exact text**
   of `src/Pallas.sol` in which only the constants P, Q, B, GX and GY are substituted. Both small
   curves are prime-order with a = 0, like Pallas, and both have Q > P, as Pallas does.
   - **E1:** y² = x³ + 5 over F_223, 229 points. For every scalar k in [0, Q + 40) and every curve
     point, `isDiscreteLogOf(k, x, y)` holds exactly when 0 < k < Q and [k]G = (x, y). The
     reference is independent affine arithmetic. Non-canonical coordinates are rejected for every k.
   - **E2:** y² = x³ + 3 over F_4987, 5023 points. Every scalar is checked against the reference,
     and k + Q is rejected.
2. **On the real curve:**
   - test vectors shared with the Rust implementation;
   - fuzzed homomorphism, 2,000 runs: [a]G + [b]G = [a+b]G;
   - negation and doubling, 1,000 runs;
   - structured scalars.
3. **Halmos (`PallasHalmos`).** Range and canonicality guards are proved: k = 0, k ≥ Q, and
   x, y ≥ P are rejected; the identity cases of `dbl` and `maddG` are also proved. The properties
   `check_dbl_ZnonZero`, `check_maddG_ZnonZero` and `check_formulas_canonical` **time out**. They
   are covered by (1).

## 4. Mutation testing

`audit/halmos_mutants.py` applies one mutation at a time to a scratch copy. Escrow mutants are
applied to the stub copy; Pallas mutants to `src/Pallas.sol`. It then reruns the checks meant to
catch that mutation. For curve-guard mutants, Halmos can pass vacuously, because the arithmetic
behind the guard is out of its reach, so the runner also runs the concrete regression tests.

## 7. Findings

**L-01 (Low, fixed): fee-on-transfer tokens made the escrow insolvent.** `open` credited `amount`
even when fewer tokens arrived. `open` now reverts with `UnsupportedToken` unless the escrow's
balance rises by exactly `amount`. Regression tests: `test_FIXED_L01_*` and
`test_feeOnTransferTokenRejected`. Mutant M20 checks it.

**I-01 (Informational, fixed): non-canonical coordinates.** `isDiscreteLogOf` compares coordinates
mod P, so (x + P, y) was accepted as the point (x, y). The escrow was not exploitable, because
`open` stores coordinates that `isOnCurve` has accepted, but the library is now strict. Regression
tests: `test_FIXED_I01_*` and `test_nonCanonicalCoordinatesRejected`. Mutant M21 checks it.

**I-02 (Informational): log order under token reentrancy.** A malicious token can re-enter during
`open` or `withdraw`. A `Refunded` or nested `Withdrawn` event can then appear before the outer
`Opened` or `Withdrawn`. Accounting stays exact (§2, M13, M18). Indexers must not assume that
`Opened` comes first for an id. The Cloakroom node reads state, not event order.

**I-03 (Informational; Slither `reentrancy-balance`, ranked High): stale balance in the L-01
check.** The balance is read before `transferFrom` and compared after it, so a re-entrant call
during the pull is included in the measured delta. This is not exploitable: every nested escrow
operation is balance-exact on its own. A nested `open` runs the same delta check. A nested
`withdraw` lowers the credits by exactly the amount it transfers out. Nested changes to the balance
are therefore matched by equal changes to the credits, and `delta == amount` implies the outer pull
delivered exactly `amount`. Per-token solvency (balance ≥ credits) is preserved. The argument fails
only for a token whose transfers move a different amount from what its `balanceOf` reports, and
such a token can break any balance-based check. The defense against it is I-04.

**I-04 (Informational): the token is chosen by the maker.** The escrow accepts any token. Safety
for the taker therefore depends on the taker's check that the escrow's `token` is the expected
USDC contract. That check is one of the 11 escrow checks in `node/src/taker.rs`. Swaps in different
tokens are isolated, because credits are kept per (token, owner).

**I-05 (Informational): reveal close to the deadline.** As in every HTLC, a `claim` broadcast just
before `lockedAt + W` can be delayed past it, and then the maker refunds instead. Wallet rule R2r
reveals only while `now + D + F + margin < lockedAt + W`, so the reveal is *final* before the
deadline, not merely included. The TLA+ model checks this (`formal/`).

## 8. What is not proven

- **Unbounded state-space safety.** Sequence proofs cover depth ≤ 2 for any swaps, depth 4 for one
  swap, and one directed depth-6 path. Unrestricted depth 3 did not terminate. Beyond that, the
  evidence is fuzzing (5 × 10⁶ calls) and the TLA+ model of the protocol, which abstracts the
  contract.
- **Curve formulas on the real field.** These are covered by exhaustive checks on two small curves
  that run the same source text, plus tests and fuzzing on Pallas. They are not proved symbolically.
- **Compiler and EVM correctness.** solc via_ir is trusted, and so are the `ecrecover` precompile
  and Base's EVM.
- **Token behaviour beyond ERC-20 returns.** Pausable or blocklisting tokens can delay `withdraw`.
  An issuer freezing a credited owner is outside the protocol's control.
- **Cross-chain properties** (no hostage, atomicity). These are argued in the paper and
  model-checked in TLA+, not proved about this bytecode.
